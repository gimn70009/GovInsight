# AI 모듈 실행 안내

FastAPI가 작업을 접수하고 Playwright로 공고를 수집합니다. PDF·HWP·HWPX·DOCX·XLSX·ZIP을 읽어 회사 관점의 분석과 초안을 생성하며, 결과 저장은 Spring Boot에 맡깁니다.

[프로젝트 소개](../README.md) · [전체 설계](../docs/DESIGN.md)

## 설치

Python 3.12가 필요합니다. 아래 명령은 **`ai` 폴더에서** 실행합니다.

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m playwright install chromium
```

설정 파일이 없는 경우에만 복사합니다.

```powershell
if (!(Test-Path .env)) { Copy-Item .env.example .env }
```

`.env`의 `OPENAI_API_KEY`를 입력합니다. 키가 들어간 파일은 커밋하지 않습니다.

| 설정 | 용도·기본값 |
| --- | --- |
| `OPENAI_API_KEY` | 실제 분석·초안 생성에 필요한 API 키 |
| `OPENAI_MODEL`, `PROPOSAL_MODEL` | 분석·제안 모델, 기본 `gpt-5-mini` |
| `SPRING_BOOT_BASE_URL` | 결과를 전달할 백엔드, 기본 `http://127.0.0.1:8080` |
| `ANALYSIS_CONCURRENCY` | 문서 분석·후속 사업 제안 생성의 단계별 동시 처리 수, 기본 `3` |

처리 시간·재시도·ZIP 제한은 [.env.example](.env.example)에서 확인할 수 있습니다. 기존 `.env`의 `ANALYSIS_CONCURRENCY`가 `2`이면 `3`으로 변경하고 AI 서버를 재시작합니다. 실행 환경에 별도로 지정한 값은 `.env`와 코드 기본값보다 우선합니다.

## 실행

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

- [상태 확인](http://127.0.0.1:8000/health): 정상 응답은 `{"status":"UP"}`입니다.
- [API 문서](http://127.0.0.1:8000/docs): 내부 작업 요청과 응답 형식을 확인합니다.
- 전체 모니터링은 [백엔드](../backend/README.md)도 실행한 뒤 화면에서 시작합니다.

Windows용 UUID·해시 호환 모듈을 사용하도록 `ai` 폴더의 가상환경 Python으로 실행합니다. 별도의 네이티브 모듈 차단 여부는 해당 PC 정책에 따라 달라질 수 있습니다.

## Windows 애플리케이션 제어 정책과 tiktoken 오류

`ImportError: DLL load failed while importing _tiktoken: 애플리케이션 제어 정책에서 이 파일을 차단했습니다.`는 `langchain_openai`가 가져오던 네이티브 토크나이저의 로드 차단입니다. 이 상태에서는 Uvicorn의 재로더 시작 메시지가 보여도 실제 AI 앱은 시작되지 않습니다. 정책 변경이나 DLL 예외 등록 없이 실행하도록 `langchain-openai` 의존성을 제거하고 `app/core/openai_models.py`에서 OpenAI SDK를 직접 연결합니다. LangChain·LangGraph의 에이전트 실행 구조는 유지합니다.

`ai` 폴더에서 의존성을 동기화하고 기존 AI 실행을 종료한 뒤 다시 시작합니다.

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

기존 가상환경에 남아 있는 `langchain-openai`·`tiktoken`은 더 이상 불러오지 않습니다. 의존성 설치 명령은 기존 패키지를 자동 삭제하지 않습니다. 새 가상환경에서는 두 패키지가 필요하지 않습니다. 모든 네이티브 라이브러리를 제거한 것은 아니며 이 수정은 로그에 확인된 `_tiktoken` 경로를 제거합니다.

모델 응답은 기존과 같이 엄격한 JSON Schema와 Pydantic으로 검증하고, 거절·미완료·파싱 실패를 정상 결과로 처리하지 않습니다. 기존 시간 제한·재시도 수·모델 설정과 도구 호출·진단 콜백을 유지합니다. 임베딩은 검색용 프로필을 문자열로 직접 전송하며 입력당 UTF-8 8,000바이트, 배치당 32개로 제한합니다. 초과 입력을 잘라서 저장하지 않고 기존 임베딩 실패 처리로 넘깁니다.

Vite의 `/api/... ECONNREFUSED`는 프록시 대상인 Spring Boot 8080 연결 실패입니다. AI 8000의 상태와 별도로 백엔드 실행 상태를 확인합니다. AI 재시작만으로 8080 연결 실패가 해결되지는 않습니다.

## 새 패키지 없는 표 파싱

HWP·HWPX·DOCX·XLSX에서 셀 위치와 명시된 병합 범위를 읽어 행/열을 구분합니다. DOCX·XLSX는 기본 ZIP/XML 기능을 사용하며 이번 변경을 적용하기 위한 추가 설치는 없습니다. 빈칸으로 필수 여부나 제출 시기를 추정하지 않습니다.

파일별 파서를 필요할 때 불러오므로 해당 파서의 import가 정책에 차단되면 그 첨부만 실패로 남깁니다. 필수 Python 런타임까지 정책 차단에서 보호하는 기능은 아닙니다. PDF는 pypdf의 텍스트/배치 추출과 아래의 선택적 VLM OCR을 사용합니다. 구형 DOC/XLS·Office 자동화는 추가하지 않습니다. XLSX 수식은 저장된 결과만 읽고 다시 계산하지 않습니다.

AI와 백엔드를 재시작한 뒤 새로 다운로드·파싱하는 문서부터 적용됩니다. 이미 저장된 첨부 텍스트는 자동 변경하지 않습니다. 기존 자료의 표 경계를 복구하려면 원본 재파싱이 필요하며 AI 재분석만으로는 복구되지 않습니다.

## HWP·HWPX·PDF VLM OCR와 비용 제한

HWP·HWPX는 **원본 구조를 WebAssembly로 렌더링 → 로컬 PDF 변환 → OpenAI VLM OCR** 순서로 처리합니다. 원본 PDF는 변환 없이 같은 OCR을 사용합니다. 기존 Playwright Chromium을 재사용하며 한글/Office 설치·COM·추가 Python DLL·유료 변환 서버를 사용하지 않습니다.

한글 변환용 JS/WASM 데이터 파일을 한 번 설치합니다. 버전과 SHA-512/256을 고정하고 npm 설치 스크립트나 네이티브 모듈을 실행하지 않습니다.

```powershell
# ai 폴더에서 실행
.\.venv\Scripts\python.exe scripts/install_hwp_renderer.py
```

현재 개발 환경에는 설치·검증을 완료했습니다. 다른 환경에서는 기존 설치 절차의 Chromium도 필요합니다. Windows의 맑은 고딕을 로컬에서 읽으며, 다른 OS에서는 `HWP_PDF_FONT_PATH`에 한글을 지원하는 TTF 경로를 지정합니다. 렌더러는 `ai/.hwp-renderer/0.8.7`에 저장되고 Git에서 제외됩니다. [공식 @rhwp/core 저장소](https://github.com/edwardkim/rhwp/tree/v0.8.7)의 MIT 라이선스를 설치 파일과 함께 보존합니다.

```dotenv
VLM_OCR_ENABLED=true
VLM_OCR_MODEL=gpt-5-mini
VLM_OCR_MAX_PAGES_PER_FILE=2
VLM_OCR_MAX_FILES_PER_DOCUMENT=2
VLM_OCR_MAX_CALLS_PER_DOCUMENT=4
VLM_OCR_PAGE_TIMEOUT_SECONDS=120
VLM_OCR_TIMEOUT_SECONDS=240
VLM_OCR_MAX_OUTPUT_TOKENS=4096
# Windows 기본 폰트를 사용할 때는 비워 둡니다.
HWP_PDF_FONT_PATH=
```

기존 `OPENAI_API_KEY`를 재사용하고 위 값이 코드 기본값입니다. AI 서버 재시작 후 새로 다운로드·파싱되는 문서에 적용됩니다. 기존 `.env`의 `VLM_OCR_MAX_CALLS_PER_RUN`은 더 이상 사용하지 않습니다. 삭제하고 위 게시글별 설정을 사용합니다. 파일 수·페이지 수는 각각 1~2, 게시글 호출 수는 1~4로 낮출 수 있습니다. OCR을 끄려면 `VLM_OCR_ENABLED=false`로 설정합니다.

- **파일당 최대 2페이지**: 제출서류·구비서류 페이지 1개와 신청자격·지원대상·참여요건·지원 제외/제한 페이지 1개를 우선 선택합니다. 목차를 제외하고 짧은 제목과 관련 표현을 점수화합니다. 두 주제가 같은 페이지에 있으면 한 번만 호출합니다. 원문 안의 여러 페이지에 걸친 요건을 모두 읽는 기능은 아닙니다.
- **게시글당 최대 2개 파일·4회**: 게시글마다 예산을 새로 배정합니다. 같은 게시글의 HWP/HWPX/PDF 및 ZIP 내부 개별 문서가 두 파일 한도를 공유하고, OCR 후보가 있는 파일을 수집 순서대로 선택합니다. 각 파일이 1페이지만 필요해도 세 번째 파일로 확장하지 않습니다. 실패 또는 캐시 사용 파일도 파일 수에 포함하며 실패 요청도 호출 수에 합산합니다. 자동 재시도는 없습니다. 후보가 없는 파일은 파일 수를 사용하지 않습니다.
- **게시글 7개면 최대 28회**: `7 × 2파일 × 2페이지`이며, 기존 모니터링 전체 4회 상한은 적용하지 않습니다. 같은 내용의 HWPX/PDF도 별도 파일로 계산하므로 형식 간 중복 제거를 보장하지 않습니다. 두 주제가 같은 페이지이거나 캐시를 사용하면 실제 API 호출은 줄어듭니다. 공고 분석·보고서·신청자격 정리의 모델 호출은 이 OCR 한도와 별도입니다.
- 제목이 없거나 텍스트가 없는 스캔은 주제를 미리 확정할 수 없습니다. 남는 슬롯에는 기존 표·스캔 후보를 페이지 순서로 넣습니다. 후보 선택은 휴리스틱이므로 실제 제출서류/자격 페이지를 놓칠 수 있습니다.
- 한글 변환은 오프라인이며 문서를 외부 변환 서버에 보내지 않습니다. 브라우저의 네트워크 요청을 로컬 자산 목록으로 제한하고 SVG의 스크립트·외부 참조를 거부합니다. 문서 내장 `data:image/svg+xml;base64` 그림과 페이지 SVG는 같은 구조 검사로 처리합니다. 도형 모양을 개별 등록하지 않고 경로·글자·그라디언트·마스크·필터·내부 참조·일반 인라인 스타일·내장 이미지를 지원합니다. 내장 SVG는 최대 3단계까지 같은 검사를 반복합니다. 스크립트·이벤트·외부 참조·활성 요소는 계속 거부하며, 요소를 조용히 삭제하지 않고 기존 파서로 복귀합니다. 파일 20MiB·100페이지·개별 원본 SVG 4MiB·전체 SVG 100MiB 한도가 있습니다. 큰 문서는 SVG 20MiB 이하 묶음으로 나눠 출력한 후 순서대로 합치고, 묶음 및 최종 페이지 수를 확인합니다. 원본/정제 SVG 중 큰 값을 합산하고 정제된 단일 페이지도 20MiB 이하로 제한합니다. 중간 PDF 합계와 최종 PDF는 각각 40MiB 이하입니다. 변환 비동기 작업 45초·프로세스당 동시 1개를 유지하며, 동기 PDF 병합·텍스트 추출의 즉시 중단을 보장하는 CPU 상한은 아닙니다.
- **텍스트 일치가 OCR의 선행 조건은 아닙니다.** 기존 추출문의 글자 중복·숫자·표 읽기 순서가 다르다는 이유로 OCR 호출이나 정상 형식의 OCR 응답을 거부하지 않습니다. 모델은 PDF 화면을 기준으로 읽습니다. 렌더러/폰트/Chromium 누락·정책 차단·시간 초과 또는 응답 형식 오류가 있으면 기존 추출문을 유지합니다.
- 페이지별 SVG ID와 참조를 분리해 여러 페이지를 합칠 때 표 자르기 영역이 충돌하던 문제를 수정했습니다. 한글 OCR 결과는 페이지 번호와 함께 앞에 추가하고 기존 한글 전체 추출문은 뒤에 보존합니다. 선택하지 않은 페이지의 정보를 변환 PDF 추출문으로 덮어쓰지 않습니다. 두 추출 방식의 내용이 중복될 수 있으며, 원본 한글 프로그램과 완전히 같은 배치나 모델 전사의 정확도를 보증하지는 않습니다.
- 선택한 최대 2페이지는 동시에 OCR하며 실제 API 요청은 프로세스 전체에서 최대 2개만 실행합니다. 같은 파일에서 동일한 페이지가 선택되면 진행 중인 요청도 공유합니다. 첫 페이지가 실패해도 다른 선택 페이지는 계속 처리하고 성공한 결과를 유지합니다. 따라서 기존 순차 방식의 실패 즉시 중단보다 실제 요청이 늘 수 있지만 게시글당 최대 4회·파일당 2페이지·재시도 없음은 유지합니다.
- OCR 요청당 PDF 2MiB·기존 페이지 텍스트 12,000자·출력 4,096토큰, 페이지당 OCR 응답 120초·파일 전체 OCR 처리 240초를 적용합니다. 각 페이지 요청에 새 제한을 배정하고 파일 전체 제한도 함께 적용하며, 응답 스트리밍 시간도 포함합니다. 동시 요청 슬롯의 대기는 파일 전체 시간에 포함하고 페이지 제한은 슬롯 획득 후 시작합니다. 대기 중 취소된 페이지는 호출 수에 포함하지 않습니다. `VLM_OCR_PAGE_TIMEOUT_SECONDS`는 1~300초, `VLM_OCR_TIMEOUT_SECONDS`는 1~600초입니다. 기존 `.env`의 45초를 유지하면 파일 전체 제한도 계속 45초이므로 위 설정으로 갱신해야 합니다. 한글 변환 45초와 OCR 시간은 별도이며, 백엔드의 전체 수집 복구 제한(기본 1시간)은 그대로 적용됩니다. 검증 성공 페이지는 최대 128건·24시간 메모리 캐시로 재사용하며 재시작·퇴출·만료 후 다시 호출될 수 있습니다. 게시글의 파일 수 또는 호출 예산을 이미 소진한 한글 파일은 변환 자체를 건너뜁니다.
- 요청 수 제한은 **월간 금액 상한이 아닙니다.** 반복 모니터링마다 비용이 누적될 수 있습니다. 모델 오류·거절·잘린 응답·불완전한 표 구조는 원래 추출문과 경고를 남깁니다. 선택한 페이지가 모두 처리됐으면 다른 후보가 더 있더라도 페이지 한도 경고를 만들지 않습니다.
- `vlm_ocr` 로그의 `candidates`는 후보 수, `selected_pages`는 선택한 PDF 페이지 번호(1부터), `requests`는 이번 파일의 실제 요청 시도 수, `cache_hits`는 캐시 사용 수입니다. `document_key`는 게시글 URL의 해시 식별자, `document_files/file_limit`는 게시글 내 OCR 대상 파일 수/한도, `document_calls/document_call_limit`는 게시글 누적 요청/한도입니다. `stop_reason`은 `completed`·`document_file_limit`·`document_call_limit`·응답 오류·`page_timeout`·`file_timeout`을 구분합니다. 실제 적용된 `page_timeout_seconds/file_timeout_seconds`와 `error_code`, 페이지별 결과 `page_results`도 남깁니다. 예를 들어 `page_results=16:completed,4:transcription_incomplete`는 16페이지 성공·4페이지 전사 미완료입니다. `cache_hits`에는 동일 페이지의 진행 중 요청 결과를 공유한 경우도 포함됩니다. `output_token_limit`는 응답 출력 한도, `transcription_incomplete`는 모델의 불완전 전사 표시, `table_structure_invalid`는 셀 누락·중복 등의 구조 오류입니다. 그 밖에 응답 미완료·거절·JSON/스키마·HTTP·시간/크기 제한을 구분하며 실제 응답 본문은 기록하지 않습니다. `error_code`가 없는 과거 `ValueError` 로그만으로 정확한 원인을 확정할 수는 없습니다. 한글 대체 처리 로그에는 `document_key`·파일 내용 해시 `file_key`·`stage=conversion/ocr`와 고정된 원인 `code`를 남깁니다. 알 수 없는 오류는 `unclassified_error`로 표시하고 예외 본문·원문·경로는 기록하지 않습니다.

`store=false`를 사용하며 별도 Files 업로드나 원문 로그는 없습니다. 기존 Python/Chromium 런타임 자체의 정책 차단까지 보장하는 기능은 아닙니다. 기존 첨부는 자동 재파싱하지 않으며 **AI 재분석만으로 변환/OCR이 실행되지는 않습니다.**

검증은 실제 로컬 HWP·HWPX 변환과 모의 OpenAI 요청을 사용합니다. 유료 모델 호출·실제 OCR 인식 품질·청구액은 측정하지 않았습니다. 선택적 실제 변환 테스트는 설치 후 다음처럼 실행합니다.

```powershell
$env:HWP_RENDERER_INTEGRATION='1'
.\.venv\Scripts\python.exe -m pytest tests/domains/monitoring/test_hwp_renderer_integration.py -q
```

## 수집 결과 전달 실패 처리

수집 결과는 동일한 실행 ID·작업 ID·본문으로 총 3회까지 전송합니다. 네트워크 오류와 HTTP 5xx·429만 0.2초·0.4초 간격으로 재시도하고, 다른 4xx는 즉시 중단합니다. 기존 `SPRING_BOOT_TIMEOUT_SECONDS`는 각 요청에 적용합니다.

수집·첨부 보강·결과 요청 구성 자체가 중단되면 소스 전체의 실패를 백엔드에 통지합니다. 통지 실패나 프로세스 종료는 백엔드의 수집 대기 시간 초과 정리로 처리합니다. 개별 첨부 오류의 부분 성공 처리는 유지합니다. **콜백 중복 방지가 적용된 백엔드를 먼저 업데이트**한 다음 AI 모듈을 재시작하세요. 중복·만료 콜백의 빈 `data.documents` 응답은 정상 처리합니다.

## 보고서 제출 안내 모델

보고서 생성 시 `gpt-5-mini`가 대상·기한·제출처·문의·서류를 원문 근거와 함께 추출합니다. 사업 제안이 없어도 동작하며 저장 체크리스트는 후보로만 사용합니다. 모델이 원문에서 확인한 서류·제출 조건으로 목록을 구성하고, 확인되지 않은 기존 항목은 자동 복사하지 않습니다. 보고서 전체 문장 생성이나 발송 단계에는 모델을 호출하지 않습니다.

기존 `OPENAI_API_KEY`를 사용합니다. 기본 활성화이며 `REPORT_BRIEF_ENABLED=false`로 끄면 기존 템플릿 추출만 사용합니다. `.env.example`의 `REPORT_BRIEF_*` 설정으로 모델, 추론 강도, 입력 길이, 시간과 동시 처리 상한을 조정합니다. `REPORT_BRIEF_REASONING_EFFORT`의 기본값은 `low`이며 `minimal`, `low`, `medium`, `high`를 허용합니다. 추론 강도는 캐시 키에도 포함됩니다. 기본은 공고당 30초/전체 기본 60초·최대 90초/동시 3건/16,000자입니다. 실패는 해당 공고만 대체 처리하며 보고서 하단에 안내합니다.

전체 제한은 `min(최대 시간, max(기본 시간, ceil(필요한 고유 모델 호출 수 / 동시 처리 수) × 공고당 제한))`로 계산합니다. 캐시 적중·동일 입력 공유·확인된 사실 재사용·호출할 원문/키가 없는 문서는 호출 수를 늘리지 않습니다. 기본 설정에서 새 호출 1~6건은 60초, 7건 이상은 90초입니다. 모든 연장은 최초 배치 시작을 기준으로 하며 대기 시간도 포함합니다. 상한에 도달하면 완료 결과를 보존하고 남은 호출을 취소해 기존 추출로 대체합니다.

`REPORT_BRIEF_TOTAL_TIMEOUT_SECONDS`는 기본 시간, 새 `REPORT_BRIEF_MAX_TOTAL_TIMEOUT_SECONDS`는 최대 시간입니다. 기존 설정이 60초이고 새 변수를 생략하면 자동으로 최대 90초까지 적용됩니다. 두 값을 모두 60으로 지정하면 기존 고정 제한을 유지합니다. 기본 시간은 최대 시간 이하여야 하며 최대 시간은 90초를 넘길 수 없습니다. 백엔드의 120초 복구 임대 전에 접수·렌더링·결과 전달 여유를 남기기 위한 제한입니다. Python 서버 재시작 후 새 보고서 생성부터 적용합니다.

같은 입력은 프로세스 메모리의 최대 256개/24시간 캐시로 재사용합니다. 재시작 후에는 다시 호출될 수 있습니다. 저장된 보고서 재발송에는 모델 호출이 없고 기존 보고서 내용도 자동 변경되지 않습니다. 모델 출력을 원문 인용과 대조해도 의미 해석 오류나 누락이 모두 해결되는 것은 아닙니다.

백엔드는 최소 보고서와 보강 요청을 먼저 DB에 저장합니다. 보고서 요청의 선택 필드 `jobId`가 있으면 Python은 이를 접수 응답과 결과 전달에 그대로 사용합니다. 결과 전송 실패 시 백엔드가 임대 만료 후 새 시도 ID로 다시 요청하며, 이전 ID의 늦은 결과는 기존 본문을 덮어쓰지 않습니다. 백엔드와 Python을 함께 재시작해 계약을 적용하세요.

첨부 입력은 총 120,000자/파일당 40,000자 안에서 분량을 배분하여 뒤쪽 공고문 누락을 줄입니다. 모델 입력 16,000자는 공고·접수 안내를 우선 배정합니다. 누락된 필드는 저장 분석 문장이 아닌 표제가 있는 원문 구절로만 보완합니다. 기존 보고서는 재전송이 아니라 새 보고서 생성이 필요합니다.

기존 환경변수에 `REPORT_BRIEF_MODEL=gpt-5-nano`가 지정되어 있으면 기본값 변경보다 우선합니다. mini를 적용하려면 `REPORT_BRIEF_MODEL=gpt-5-mini`로 바꾼 뒤 AI 서버를 재시작하세요. PDF 줄 복원은 새 파싱부터 적용되며 기존 파싱 결과의 재사용은 별도입니다.

## 분석 시도 ID와 보고서 조건 검증

`POST /internal/monitoring/analysis-jobs`의 선택 UUID `jobId`는 백엔드 복구 작업이 지정한 시도 ID입니다. 지정된 경우 접수 응답과 분석·제안 콜백에 같은 값을 사용하며 생략하면 기존처럼 생성합니다. 백엔드는 만료·이전 시도의 결과를 409로 거부합니다. Python의 프로세스 내 작업 자체가 영속화되는 것은 아니며 백엔드 DB 작업이 중단을 복구합니다.

보고서 표시 검증은 수치·단위·비교 방향을 함께 검사합니다. 한국어 자격 제한·부정·예외 조건은 검증된 원문 인용 전체를 보존하고, 길거나 역할 연결이 불명확한 자격 표는 원문 확인 안내로 남깁니다. 모든 자연어 의미 오류를 보장해서 제거하는 기능은 아니며 기존 저장 보고서는 자동 변경하지 않습니다.

## 제안·보고서 모델 지연 진단

Python 서버를 재시작한 뒤 새 모니터링을 실행하면 기존 콘솔에 `model_call_*`, `report_brief_*` 진단이 추가됩니다. 진단 자체는 별도 설정이나 추가 API 호출이 없으며 모델·재시도·결과 상태 정책을 바꾸지 않습니다. 보고서의 동적 시간 제한은 위 제출 안내 모델 설정을 따릅니다.

- `model_call_start/stage/progress/finish`: `call_id`로 한 호출을 추적합니다. 제안은 `detection_id/version_id`, 보고서는 `run_id/version_id`로 공고를 구분합니다. 실제 모델 설정, 시간 제한, 입력/원문 문자 수, 구간별 경과 시간이 기록됩니다. 대기 중에는 15초마다 현재 단계가 표시됩니다.
