## 계속 진행 중으로 보이는 이유

- `ai/app/domains/analysis/clients/analysis_result_client.py`는 4xx 응답을 받으면 결과 전달을 중단하며 HTTP 상태 코드만 오류에 포함한다. 서버의 응답 본문이나 필드별 거절 이유는 현재 로그에 남기지 않는다.
- `ai/app/domains/analysis/tasks.py`는 결과 전달 실패를 기록하고 반환한다. 이후 사업 제안 처리에도 도달하지 않는다.
- `AnalysisTaskService`의 기본 작업 대기 시간은 문서당 15분이다. 14건이면 수집 후 분석 접수 시점부터 210분 동안 기존 시도가 유효하다. 실패 통지가 별도로 저장되지 않아 분석 작업이 `RUNNING`으로 남는다.
- 실행은 보고서 저장 이후에야 완료되므로 화면도 진행 중 상태를 유지한다. 백엔드가 계속 실행된다는 전제에서 11:27:56 이후 복구 주기가 재시도를 시작할 수 있는 것이며, 그때 성공한다는 의미는 아니다.

## 후속 원인 확정: Unicode 길이 계산 불일치

사용자의 후속 원인 확인 요청으로, 그대로 살아 있던 Python 작업 프로세스에서 위 실행 ID·분석 시도 ID와 정확히 일치하는 전송 JSON만 읽기 전용으로 복원했다. 프로세스 변경이나 전체 메모리 덤프는 하지 않았다. 14개 결과·실패 0개의 실제 요청을 당시 백엔드의 컴파일된 DTO와 Hibernate Validator에 오프라인 재생했다.

- **위반은 정확히 1개:** `results[12].comparisonSummary.legalRisks[2].evidenceExcerpt`의 `@Size(max=3000)`.
- 대상은 문서/버전/감지 ID 13, **2027년 스마트공장 구축지원사업 모집공고**의 `RESULT_IP_REUSE` 근거 인용문이다.
- Python의 문자 수는 **2,995 코드 포인트**, Java의 문자 수는 **3,014 UTF-16 코드 단위**였다.
- 인용문에 보충 평면 사설 영역 문자 `U+F02B1` 7개, `U+F02B2` 7개, `U+F02B3` 5개가 포함되어 있다. 19개 모두 Python에서는 한 문자, Java String에서는 두 코드 단위여서 차이가 발생했다.
- Python `LegalRiskFinding.evidence_excerpt`의 `Field(max_length=3000)`은 통과하지만 Java `AnalysisResultRequest.LegalRiskFinding.evidenceExcerpt`의 `@Size(max=3000)`는 거절한다. 실제 요청 전체를 Python에서 새로 검증해도 통과했다.
- DB에 보존된 원래 분석 입력에서 13번 문서만 읽어 `find_legal_risk_candidates`를 재실행했다. 해당 HWPX 첨부에서 추출된 후보가 실제 실패 인용문과 **완전히 일치**하며 `incomplete=false`였다. 모델이 새로 만들어 낸 인용문이 아니라 원문에서 복원한 근거였다.
- 진단 전용 복사본에서 보충 평면 문자 19개만 단일 UTF-16 문자로 치환하면 다른 필드를 그대로 둔 14건 전체의 Java 검증 위반이 **1개에서 0개**로 바뀌었다. 이 복사본은 실제 서비스에 전송하거나 DB에 저장하지 않았다. 원문을 치환하는 방식을 제품 수정으로 채택한 것도 아니다.

따라서 이번 실패의 직접 원인은 Python/Java 사이의 문자열 길이 제한 단위 불일치다. 한 건의 근거가 배치 요청 검증에 걸려 14건 전체가 서비스 저장 단계에 들어가지 못했다. 결과 전달 거절을 실행 실패로 반영하지 않고 210분의 회수 대기 시간을 유지하는 문제가 장시간 진행 중 표시를 만들었다.

복원본·원래 입력·대조 파일과 진단 도구는 Git에서 제외된 `backend/build/`에만 보관하며 원문·회사 정보는 이 문서에 싣지 않는다. 원래 HTTP 오류 응답 본문 자체는 보존되지 않았지만 실제 전송 본문으로 위반을 재현했으므로 이전 점검의 필드 미확정 한계는 해소되었다.

## 수정 및 검증

초기 점검과 원인 확정 단계에서는 제품 코드·DB 쓰기를 하지 않았다. 이후 사용자의 수정 요청에 따라 다음을 반영했다.

- 분석·제안 결과 DTO의 문자열 길이 제한을 Hibernate Validator `@CodePointLength`로 변경했다. 기존 숫자 제한과 목록 개수·필수값 검증은 유지하며, 인용문이나 특수문자를 삭제·치환·절단하지 않는다.
- Python 클라이언트가 HTTP 4xx(429 제외)를 받으면 새 `/internal/monitoring/analysis-result-failures`에 실행 ID·시도 ID·분석/제안 단계·상태 코드만 통지한다. 백엔드는 실행 행 잠금 아래 현재 COLLECTED 실행, 유효한 동일 시도, 해당 단계(RUNNING/ANALYZED)가 일치할 때 작업과 실행을 FAILED로 정리한다.
- 다음 단계로 진행한 성공 결과, 완료된 작업, 이전/만료 시도, 중복 통지와 429는 상태를 변경하지 않는다. 통지 오류는 원래 오류를 덮지 않고 기존 제한 내에서 재시도한다. 전체 백엔드 장애나 통지 유실은 기존 임대 복구의 범위로 남는다.
- HTTP 거절 로그는 상태와 길이/형식을 제한한 필드 경로만 포함하며 응답 메시지·원문·인용문·회사 정보를 기록하지 않는다.

## 기존 대기 실행 정리

이미 끝난 Python 작업은 새 실패 통지를 보내지 않으므로, 사용자의 수정 요청 범위에서 기존 실행 차단도 해제했다. 백엔드가 종료된 상태에서 실행 1번과 작업 1번을 잠그고, COLLECTED/RUNNING·시도 1회·동일 UUID·수집 14건·저장 분석 0건을 확인한 뒤 전체 기존 행과 요청 JSON을 `backend/build/monitoring-rejection-before-20261124.json`에 백업했다.

해당 두 행만 FAILED로 변경하고 실행 완료 시각·안전한 안내를 기록했다. 작업의 요청 JSON은 기존 실패 정책처럼 정리했으며 백업본과 복원된 결과 14건은 유지한다. 전후 수집 문서·첨부 건수 일치와 커밋 후 상태를 재조회했다. 실행/작업 1번 모두 FAILED이고 7개 기관·공고 14건의 수집은 보존되었다. 저장 분석은 0건, 보고서는 0건으로 그대로이며 생성 결과를 성공 저장한 것으로 표시하지 않는다. 모델 재호출·보고서 생성·알림 발송은 없다. 서버 재시작 후 수동 모니터링을 다시 실행할 수 있다.

점검 후 루트 작업 지침에 따라 8080을 점유한 백엔드 PID 5016만 종료하고 해당 포트가 비어 있음을 확인했다. Python·프런트엔드 프로세스는 종료하지 않았다. 백엔드가 종료되었으므로 위 재시도 시각은 실행 중일 때의 예정 값이며 실제 복구 완료를 의미하지 않는다.
