# 보고서 선저장·장애 복구 검증

## 변경 범위

보고서 단계 진입 시 최소 본문과 요청 스냅샷을 같은 DB 트랜잭션에 저장합니다. 보강 및 발송 작업은 DB 상태·시도 ID·임대로 관리합니다. 기본 본문을 최종 발송한 후 늦게 도착한 보강본으로 교체하거나 자동 재발송하지 않습니다.

## 검증 사례

H2 Oracle 모드에서 실제 JPA 트랜잭션/잠금을 사용하고, Python 모델 서버와 이메일/Telegram 클라이언트는 대체 객체를 사용했습니다.

- 기본 본문·요청 스냅샷 저장 후 외부 요청, 사업 제안 완료/분석 재사용 BEFORE_COMMIT 저장
- 저장 트랜잭션 롤백 시 기본 보고서와 작업이 함께 취소됨
- 동시 실행자 중 한 개만 작업을 획득, 활성 임대는 대기 조회에서 제외
- 2분 임대 만료 후 새 트랜잭션에서 작업 재개, 3회 응답 유실 뒤 기본 보고서 완료
- Python 접속 실패 3회 뒤 기본 보고서로 발송 작업 전환
- 생성 실패 콜백은 기본 보고서 확정, 이전 시도/중복/완료 후 콜백은 본문을 덮어쓰지 않음
- 발송 임대 중단과 채널별 준비 오류 복구, 한 채널 오류가 다른 채널 처리를 막지 않음
- 손상되거나 null인 요청 JSON도 이미 저장된 기본 본문으로 완료
- 벽시계가 함수 호출 사이에 진행해도 기본 보고서 확정 후 발송 임대를 정상 획득
- 작업 행이 없는 기존 PENDING 보고서 재등록, 완료된 보고서는 자동 재전송 대상에서 제외
- 이메일 외부 호출 뒤 예외로 본문 처리 트랜잭션이 롤백되어도 별도 커밋한 발송 시도는 유지, 자동 재전송 없음. 오래된 미완료 시도는 수신 여부 확인이 필요한 실패로 표시
- 최소 본문은 분석 없음·게시글 없음·위험한 URL에서도 생성하며 길이 상한을 유지
- Python 접수 API는 서버가 지정한 jobId를 접수 응답과 백그라운드 작업에 그대로 전달

## 운영 적용

- 백엔드와 Python을 함께 재시작합니다. 새 계약의 jobId가 일치하지 않으면 보강 요청이 거부되고 제한 재시도 후 기본 본문을 사용합니다.
- 로컬 기본 ddl-auto=update는 report_tasks 테이블/시퀀스를 생성합니다. validate/none 환경에서는 docs/sql/report-tasks-2026-09-22.sql을 한 번 적용한 후 배포합니다. 운영 Oracle에는 이번 검증에서 접속하지 않았습니다.
- 복구 작업은 기본 5초 간격, 프로세스 시작 후 10초부터 실행됩니다. 모델 작업은 총 3회, 임대 2분, 접수 실패 재시도 간격 10초입니다. 처리량/외부 호출 시간에 따라 실제 복구 시각은 늦어질 수 있습니다.
- 생성/발송 스케줄러는 웹 계층 통합 테스트에서 비활성화하고, 작업 서비스는 전용 DB 통합 테스트로 직접 호출했습니다.

## 한계

실제 운영 서버 강제 종료 실험, Oracle 잠금 테스트, 실제 모델·SMTP·Telegram 전송은 수행하지 않았습니다. DB에 작업을 저장한 이후의 보고서 복구를 다루며 수집/분석 단계 전체의 복구는 포함하지 않습니다. DB가 중단된 동안 새 보고서 저장/전송은 불가능합니다. 외부 발송 성공 여부가 불확실한 건은 자동 재전송하지 않으므로 수신 확인 후 수동 재전송이 필요합니다.
