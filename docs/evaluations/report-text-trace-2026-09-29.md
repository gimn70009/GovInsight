# 보고서 사업명 오류의 저장 단계 대조 (2026-09-29)

## 결론

사용자 화면의 `원-스웨덴`은 실제 저장된 `comparison_summary.purpose`에 존재한다. 수집 제목·본문, HWP/HWPX 추출문, 일반 분석 `summary`에는 `한-스웨덴`이 정상적으로 남아 있다. 보고서가 목적 문구를 일반 요약보다 우선 선택했고 이메일 HTML은 그 오기를 그대로 표시했다. 화면 잘림이나 앞서 수정한 URL 렌더링에서 생긴 변경이 아니다.

## 조회와 대조

## 전달 경로와 검증의 빈틈

1. `analysis/workflow/agent.py`의 `BaseAnalysisDraft`는 일반 `summary`와 별도 `comparison_summary.purpose`를 모델에 함께 생성하도록 요청한다. `BaseComparisonSummary.purpose`에는 길이 제한이 있지만 제목·원문 고유명사와의 일치 검사는 없다.
2. 모델 결과에서 `AnalysisDraft`를 만들고 `workflow/graph.py`가 `comparison_summary`를 결과로 전달한다. 확인한 변환 경로에 `한`을 `원`으로 치환하는 처리는 없다.
3. 백엔드 `AnalysisResultService.updateComparisonSummary`는 해당 구조를 JSON으로 저장한다. 보고서 요청도 이 저장 JSON을 전달한다.
4. `report/template.py::_brief_summary`는 `comparison_summary.purpose`가 있고 `확인하지 못` 문구가 없으면 이를 우선한다. 정상인 일반 `summary`와 대조하지 않는다.
5. 이메일 `ReportEmailTemplate`은 `요약: ` 접두어만 제거하고 내용을 그대로 렌더링한다.

따라서 관측한 최초 오류는 모델이 작성하는 별도 목적 필드의 저장값이다. 원문·첨부의 동일 사업명은 정상이고 저장 후 전달·표시 경로를 재현했으므로, 목적 생성 오류가 검증을 통과해 보고서 재사용으로 이어진 것으로 판단한다. 해당 실행의 원시 모델 응답은 따로 확보하지 않았으므로 생성 토큰 자체를 직접 관찰한 것은 아니다.

## 오프라인 재현

- 실제 DB의 제목·본문·summary·comparison_summary로 `ReportDocumentRequest`를 구성하고 `_brief_summary(..., 180)`을 실행했다. 결과가 저장된 잘못된 목적 문구와 정확히 같았다.
- 두 저장 보고서에 같은 요약 행이 있는지 확인했다.
- 진단용 입력 복사본에서 `comparison_summary`를 제외하면 일반 요약의 정상 첫 문장이 선택됐다. 운영 DB나 제품 코드에 이 변경을 적용한 것은 아니다.
- Git HEAD의 `ReportEmailTemplate`, `ReportBodyFormatter`, `YearNotation`을 별도 디렉터리에 컴파일했다. 같은 실제 보고서를 기존·현재 렌더러에 넣었을 때 모두 같은 오기가 남았다.
- 재현 결과: `backend/build/report-investigation/summary-replay.json`, `email-before.html`, `email-current.html`.

이번 확인에서 제품 코드를 추가 수정하지 않았다. 한 단어를 임의 치환하거나 모든 보고서의 요약 선택 정책을 곧바로 바꾸는 대신, 확인된 오류 단계와 영향을 기록했다. 일반 단위 테스트 통과는 실제 생성 문장의 사실 정확성을 검증했다는 뜻이 아니다.

## 앞선 URL 사례의 확인 한계

현재 DB에는 보고서 1·2만 있으며, 첫 화면에 나온 KIAT 중견기업 상생협력 접수처 문구는 없다. 기존 평가 원문에서 같은 공고의 `www.kiat.or.kr` 주소는 확인했지만, 화면과 정확히 일치하는 발송 보고서/모델 출력은 확보하지 못했다. 브라우저 도구도 로컬 샌드박스 초기화 오류로 실행되지 않았다.

앞서 추가한 일반 URL 링크·줄바꿈 처리는 표시 보완이며, 그 특정 메일의 잘림 원인을 확정한 수정으로 해석하면 안 된다. 이번 한-스웨덴 건의 저장값 대조 결과와 구분한다.


## 후속 수정: 일반 분석 요약 사용

사용자의 수정 요청에 따라 보고서가 `comparison_summary.purpose`를 사용하지 않고 `summary`의 첫 문장을 선택하도록 변경했다. 정상 요약과 잘못된 목적이 함께 있어도 목적을 보고서에 노출하지 않는다. 첫 문장이 일반형 180자·축약형 110자를 넘으면 이름·조건을 중간에서 자르지 않고 게시글 상세에서 요약 전문을 확인하도록 안내한다.

- 실제 사례를 바탕으로 신규/변경 없음, 일반형/50건 축약, 긴 첫 문장, 분석 미완료 안내, 날짜·URL 문장 경계를 검증하는 7개 회귀 테스트를 추가했다. 수정 전 7개 모두 실패한 것을 확인했다.
- 같은 DB 조회본을 수정 코드로 재생성해 `한-스웨덴`이 포함된 정상 첫 문장과 이메일 HTML의 문장 보존을 확인했다. 재현 결과는 `backend/build/report-investigation/summary-fixed.json`, `report-fixed.txt`, `email-fixed.html`에 저장했다.
- AI 전체 951개 테스트와 변경 Python 정적 검사를 통과했다. 이메일의 정상 요약 보존 회귀 테스트를 포함한 백엔드 전체 390개도 통과했다. 최종 변경 검사와 8080 포트 비어 있음을 확인했다.

변경은 새 보고서 생성에 적용된다. 저장 목적 값, 이미 생성된 보고서, 발송 이력은 수정하지 않았고 실제 재발송도 하지 않았다. 생성 단계에서 모든 사업명·국가명을 원문과 대조하는 범용 검증은 이번 수정에 포함하지 않는다. 따라서 일반 `summary` 자체에 잘못된 사실이 들어오는 문제까지 해결했다고 볼 수는 없다.
