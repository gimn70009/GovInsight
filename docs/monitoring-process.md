# 공공기관 모니터링 처리 규칙

## 문서 목적

이 문서는 공공기관 게시글을 수집하고 변경 여부를 판단한 뒤 분석 결과를 저장하고 알림을 전송하는 기능 규칙을 정의한다.

구체적인 클래스 구조나 구현 방식보다 시스템이 지켜야 하는 동작을 설명한다. 구현 방식이 바뀌더라도 이 문서의 기능 규칙은 유지되어야 한다.

## 전체 처리 흐름

1. Spring Boot가 활성화된 모니터링 소스를 조회하고 실행 이력을 생성한다.
2. Spring Boot가 Python 모듈에 비동기 HTTP 방식으로 수집·분석 작업을 요청한다.
3. Python 모듈은 작업을 접수한 뒤 즉시 접수 결과와 작업 ID를 응답한다.
4. Python 모듈은 백그라운드에서 목록과 상세 게시글을 수집하고 첨부파일을 처리한다.
5. 기존 저장 문서와 비교해 신규·수정·변경 없음 상태를 판정한다.
6. Python 모듈은 신규 또는 수정된 게시글을 LLM으로 요약하고 중요도를 판정한다.
7. 처리가 끝나면 Python 모듈이 Spring Boot의 결과 수신 API로 처리 결과를 전달한다.
8. Spring Boot는 실행 결과, 문서, 첨부파일, 감지 결과를 PostgreSQL에 저장한다.
9. Spring Boot는 전송 조건을 충족하는 사용자에게 Telegram 보고서를 발송한다.

Spring Boot와 Python 모듈의 역할, 작업 상태, 내부 API 방향은 `docs/architecture.md`를 따른다.

## 모니터링 소스

- 모니터링 소스는 개별 게시글이 아니라 게시판 목록 URL을 기준으로 등록한다.
- 활성화된 소스만 수동 실행과 자동 스케줄 실행의 대상이 된다.
- 소스를 새로 등록해도 즉시 수집하지 않고 다음 수동 또는 스케줄 실행부터 반영한다.
- 소스에는 기관명, 게시판명, 목록 URL, 상세 수집 수, 상세 URL 포함 패턴, 활성 여부 등을 설정할 수 있다.
- 상세 URL 포함 패턴은 목록 페이지의 여러 링크 중 실제 게시글 링크를 구분하는 데 사용한다.

## 게시글 수집

- 목록 페이지는 동적 렌더링과 JavaScript 기반 이동을 고려해 수집한다.
- 목록의 `tr`, `li`, `article`, 링크 및 행 클릭 구조 등 다양한 형태를 고려한다.
- 상세 페이지에서는 다음 정보를 수집한다.
  - 게시글 제목
  - 본문 텍스트
  - 게시일 추정값
  - 첨부파일 목록
  - 첨부파일 다운로드 URL
- 본문을 추출할 때 헤더, 푸터, 공유 버튼, 이전글·다음글, 만족도 조사 등 불필요한 영역을 최대한 제거한다.
- 게시일 위치와 상세 페이지 이동 방식처럼 기관마다 다른 구조는 소스별 예외로 다룰 수 있어야 한다.

## 변경 감지

- 처음 발견한 게시글은 `new_document`로 판정한다.
- 기존 게시글의 본문 또는 첨부파일 구성이 변경되면 `updated_document`로 판정한다.
- 기존 게시글과 동일하면 `unchanged_document`로 판정한다.
- 본문은 공백과 개행 등을 정규화한 후 SHA-256 해시를 계산해 비교한다.
- 첨부파일은 파일명 목록을 기반으로 만든 시그니처를 비교한다.
- 본문 해시와 첨부파일 시그니처 중 하나라도 달라지면 수정된 문서로 처리한다.
- `unchanged_document`는 다시 요약하지 않고 마지막 확인 시각과 확인 이력만 갱신한다.
- 수동 실행도 기본적으로 전체 데이터를 강제로 다시 처리하지 않고 변경분만 처리한다.

## 첨부파일 처리

- 기본 분석 대상은 PDF, HWP, HWPX 및 일부 HTML 뷰어형 첨부파일이다.
- PDF는 텍스트 레이어를 추출한다.
- HWP는 OLE 구조에서 본문 텍스트를 추출한다.
- HWPX는 ZIP/XML 구조에서 본문 텍스트를 추출한다.
- 첨부파일에서 추출한 텍스트는 게시글 본문과 함께 요약 입력으로 사용한다.
- 지원하지 않는 파일이나 파싱 실패가 발생해도 게시글 본문을 이용한 처리는 계속할 수 있어야 한다.
- 스캔 PDF처럼 텍스트 레이어가 없는 문서는 OCR이 없으면 정확하게 처리할 수 없음을 전제로 한다.

## LLM 분석

- `new_document`와 `updated_document`만 LLM 분석 대상으로 삼는다.
- 분석 결과는 다음 정보를 포함한다.
  - `summary`: 핵심 요약
  - `keyPoints`: 핵심 포인트 목록
  - `riskLevel`: `low`, `medium`, `high`
  - `relevance`: `important`, `watch`, `reference`
- 본문이 짧고 첨부파일이 없으면 직접 요약할 수 있다.
- 본문이 길거나 첨부파일이 있으면 본문과 첨부파일을 각각 요약한 뒤 최종 요약으로 합치는 단계형 요약을 사용한다.

## 저장 대상

처리 결과는 다음 단위로 구분해 저장한다.

- 모니터링 소스
- 실행 이력과 실행 보고서
- 실행별 감지 결과
- 게시글 원문과 변경 상태
- 첨부파일 정보와 추출 텍스트
- Telegram 발송 결과
- Telegram 수신자 정보

정확한 테이블명, 컬럼, 관계는 별도의 데이터베이스 설계 문서에서 정의한다.

## 실행 규칙

- 자동 스케줄 실행의 기본 시간대는 `Asia/Seoul`이다.
- 자동 스케줄 실행은 같은 날짜에 이미 실행된 기록이 있으면 중복 실행하지 않는다.
- 관리자가 요청한 수동 실행은 같은 날짜에 다른 실행 기록이 있어도 허용한다.
- 스케줄 활성화 여부와 실행 시각은 환경설정으로 변경할 수 있어야 한다.

## Telegram 전송

- 수동 실행과 자동 스케줄 실행이 완료되면 생성된 보고서를 전송할 수 있다.
- Bot Token, 유효한 Chat ID, 활성화된 수신 여부를 모두 충족하는 사용자만 전송 대상이 된다.
- 긴 보고서는 Telegram 메시지 길이 제한을 고려해 여러 메시지로 나누어 전송한다.
- 수신자별 성공, 실패, 건너뜀 상태와 오류 원인을 기록한다.
- 동일한 Chat ID의 중복 등록을 허용하지 않는다.

## 실패와 fallback

- 하나의 소스 수집 또는 분석 실패가 전체 실행을 즉시 중단시키지 않도록 한다.
- 실패한 기관, 게시판, 처리 단계와 원인을 추적할 수 있는 경고를 남긴다.
- 정상 보고서를 생성할 수 없는 경우 점검 정보를 포함한 `fallback` 결과를 저장할 수 있다.
- 외부 사이트, 브라우저, AI 모듈 또는 네트워크 상태를 점검할 수 있는 정보를 남긴다.

## 운영상 유의사항

- 기관별 게시판 구조 차이에 따라 수집 규칙을 추가로 조정할 수 있다.
- 대상 사이트의 이용정책과 `robots.txt`를 확인하고 허용 범위 안에서 수집한다.
- 요청 간격, 첨부파일 최대 개수와 최대 용량에는 운영상 제한을 둘 수 있다.
- 지원하지 않는 문서 형식이나 시각적 구조까지 완전하게 해석된다고 가정하지 않는다.
- 미확정된 제한값과 세부 구현 방식은 구현 전에 별도 설계 문서에서 확정한다.
