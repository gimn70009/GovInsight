## 2. 핵심 발견

### A. 일반 공고 판정과 실제 지원 유형 판정이 서로 충돌한다

- V16 지역 중대재해 예방 사업은 본문과 267자 첨부 모두 추가 선정 결과를 알린다. 저장된 proposal.documentType은 GENERAL_NOTICE지만 businessType은 ADOPTION이다. 설명은 설비·안전조치 도입이 “수반될 가능성이 있어”라고 추정한다. 현재 신규 모집 근거는 없다. 제목에는 “결과”가 없어서 제목 기반 선정결과 규칙이 작동하지 않고, 저장된 유형이 있다는 이유로 GENERAL_NOTICE 보완도 막힌다.
- V12 NCP도 선정결과를 ADVISORY로 저장했다. 최종 표시는 제목 규칙으로 해당 없음이 되지만 저장 분류 오류 자체는 남는다.
- V24 지원규정 개정 고시는 본문에 모집이 없다. 첨부 안의 “별도의 모집 기간을 정할 수 있다”와 규정에 딸린 운영신청서 제출 문구가 현재 모집으로 인식된다. 59,552자 규정 전체가 일반공고 판정 입력으로 남아 있었다.

코드 위치: `backend/src/main/java/com/publicmonitor/backend/domain/document/service/GeneralNoticeClassifier.java`의 matches/recruitmentBody, `BusinessTypeResolver.java`의 diagnose/stored.

### B. 원문 인용 검증이 의미까지 검증하는 것은 아니다

저장 유형이 있는 V12·V16·V23은 현재 Python과 Java의 인용 검증을 모두 통과한다. 원문 발췌의 출처·문자열 일치는 확인되지만, 해당 문장이 선택한 지원 유형을 입증하는지는 확인하지 않는다. 세 건 모두 저장 유형의 의미를 다시 검토해야 하며, 그중 V16·V23은 최종 유형 표시에도 그대로 반영된다.

V23의 근거는 선도사업자 선정과 기금 우선지원·우대금리인데 결과는 설비·시스템 도입이다. 대상 기업의 공급망 활동과 실제 제공되는 혜택을 혼동했다.

### D. 시범사업은 원문이 있어도 규칙이 놓친다

V14 재생에너지 출력기준 자율접속제도는 4,599자 첨부가 모두 파싱되어 있다. 현재 기본 40,000자 예산으로 입력 선택을 재현해도 전체가 보존된다. 다만 당시 실제 전송 프롬프트는 저장되어 있지 않다.

- “□ 시범사업 개요”는 지원 구역 제목으로 인식되지 않는다.
- “제도에 시범적으로 참여”는 현재 행동·유형 어휘와 맞지 않는다.
- 지원내용 구역의 “시범사업 참여자의 … 발전허가 유지”는 시범사업 어휘는 있으나 행동 어휘 조건에 걸리지 않는다.

단어가 한 줄 안에 같이 있어야 하는 분류 규칙 때문에 문단의 의미를 놓친 사례다. 제목에 시범사업이 있다는 이유만으로 분류하는 처방보다, 개요·지원 내용을 하나의 근거 구역으로 읽는 수정이 적절하다.

### E. 같은 공고를 기관마다 다르게 처리한다

공급망안정화 선도사업자 통합공고의 기관별 게시본 V1·V9·V11은 확인 필요, V23은 ADOPTION이다. V11과 V23의 HWPX 추출문은 SHA-256까지 동일하다. 본문과 첨부 구성은 기관마다 다르므로 프롬프트도 완전히 같았다고 단정할 수는 없다. 공통 원문에 대한 분류 일관성 검사와 동일 공고 그룹 식별이 필요하다.

### F. null 23건의 과거 원인은 지금 자료만으로 확정할 수 없다

확인한 저장 자료에는 검증 전 모델 후보와 거절 이유가 없다. 모델이 처음부터 null을 반환했는지, 인용 검증에서 탈락해 null이 됐는지 구분할 수 없다. 23건 모두 모델 오답이라고 세면 안 된다. 선정 결과처럼 null이 정상인 공고도 포함된다.

현재 코드에서 분석 초안→검증→최종 결과→백엔드 comparisonSummary 저장 경로를 확인했으며, PROPOSAL_REQUEST라는 이유로 사업 유형을 삭제하는 분기는 발견하지 않았다. AI 검증은 근거 1개라도 실패하면 전체 유형을 null로 만든다. 직전 작업에서 넣은 진단 로그는 이후 실행을 추적하기 위한 것으로, 과거 원인을 복구하지 않는다. 향후 reason·후보 코드·검증 버전을 구조화해 보존할 필요가 있다.

### G. 파싱 성공과 분류에 충분한 원문 확보는 별개다

- V19 영문 공고 PDF: `PDF 파일을 읽을 수 없습니다.` 정확한 손상·암호화·형식 원인은 이번 조사에서 확정하지 않았다. 국문 HWP와 다른 자료가 있고 RND로 분류된다.
- V20 정부포상 업무지침 HWPX: 최대 허용 크기 초과. 주 공고문과 별도 지침은 파싱되어 있어, 이 실패가 포상 유형 미분류의 직접 원인이라고 볼 수 없다.
- V14 등 표에는 병합 셀이 반복된 추출문이 남는다. 완료 46개를 46개 모두 정확하게 복원됐다는 의미로 해석하면 안 된다.
- 입력 선택기는 추출문이 완전히 같은 첨부만 중복 제거한다. PDF/HWPX 간 표현 차이가 있는 같은 문서와 서식·지침이 입력 예산을 함께 쓰는 문제는 추가 개선 대상이다.

## 4. 권장 수정 순서와 검증 조건

아래는 최초 조사 시점의 제안이다. 이후 구현·검증한 범위는 6절에 기록했다. 기존 10개 지원 유형은 유지한다.

1. **공고 성격과 지원 유형 분리.** 사업 참여 모집, 포상·표창 모집, 지정 모집, 선정 결과, 규정·고시, 일반 안내를 먼저 구별한다. 지원 유형은 실제 현재 지원 활동이 확인될 때만 정한다. 선정 결과·규정 고시에는 일반 공고 사유를 보여주고, 포상·지정 모집은 신청 기한·참여 가능성을 보존한다. 이미 존재하는 proposal.documentType과 모순될 때의 우선순위도 명시한다. 확인 조건: V16·V24를 교정하면서 실제 모집 V2·V4·V14와 지정 모집 V1을 결과 공고로 바꾸지 않는다.

2. **근거의 의미 검증과 충돌 처리.** 발췌가 같은지뿐 아니라 현재 공고의 목적·모집 역할·실제 지원 활동이 선택 유형을 입증하는지 확인한다. “향후 가능성이 있다”는 해석만으로 지원 유형을 확정하지 않는다. 판단 충돌 때 검증된 결과 공고 성격을 우선하고, 필요한 경우 분류만 좁혀 재검토한다. 확인 조건: V12·V16·V23의 현재 인용 일치만으로 잘못된 유형을 승인하지 않는다.

3. **지원 구역 단위 전처리.** 개요·목적·지원 내용과 하위 항목을 묶어 읽고, 규정·양식·선정 결과·예시의 역할을 구별한다. 동작 단어가 한 줄에 없다는 이유로 문단 전체의 근거를 버리지 않는다. 파일명·원문 위치를 유지하고 본문을 임의로 보충하지 않는다. 주 공고문에 입력 예산을 우선 배분하며 중복 형식과 병합 셀 반복을 줄인다. 확인 조건: V14를 실증·시범으로 잡되 규정 속 신청서와 신청 자격의 인증 보유를 지원 활동으로 분류하지 않는다.

4. **추적 가능한 검증 결과 보존.** 모델 후보 코드, 최종 코드, 제외 사유, 근거 위치/ID, 모델·프롬프트·검증기 버전을 저장한다. 외부 응답에 민감한 원문을 노출하지 않는다. 거절된 근거를 무조건 무시하는 대신 해당 근거에 의존한 주장도 함께 재검증한다. 확인 조건: null을 다시 만들었을 때 모델 미분류·출처 불일치·인용 불일치·유형 범위 밖을 구별할 수 있다.

5. **실제 사례 평가 후 필요한 건만 재처리.** 이번 26건을 검토된 평가 사례로 만들되 동일 공고는 한 그룹으로 묶는다. 기관·형식별 중복을 학습/평가 양쪽에 넣지 않는다. 확인 필요를 줄인 수치와 오분류가 줄어든 수치를 따로 측정한다. 구조·검증 변경 뒤 분류만 선택적으로 다시 계산하고, 전체 분석·메일을 일괄 재생성하지 않는다. 실패한 2개 첨부는 별도로 재다운로드·형식·크기를 진단한다.

현재 자료에서는 라벨 체계·공고 성격 판정·규칙의 문단 인식·검증 추적이 먼저다. 파인튜닝이나 모델 교체가 이 문제들을 해결한다고 판단할 근거는 확보되지 않았다. 위 수정 후 독립된 실제 공고 평가에서 남는 오류를 기준으로 추가 모델 실험 여부를 결정한다.

## 5. 수행한 검증과 한계

- Oracle 연결은 `SET TRANSACTION READ ONLY`와 SELECT로만 사용하고 rollback했다. DB, 저장 분석, 첨부 상태는 바꾸지 않았다.
- 외부 OpenAI 호출, 재분석, 수집 재실행, 이메일 발송은 하지 않았다.
- 현재 코드와 b2b0b89의 BusinessTypeResolver를 동일한 26건으로 비교했다. 전체 반환 객체가 모두 같았다. 따라서 직전 “번호가 붙은 공고문 보존” 수정만으로 이번 실제 데이터 문제가 해결됐다고 말할 수 없다.
- Python 검증기에서 저장된 3개 유형의 VALIDATED를 재확인했다. null을 입력한 재검증의 MODEL_UNCLASSIFIED는 과거 모델이 null을 반환했다는 증거가 아니다.
- Java 실제 규칙을 이용해 V14의 구역·행동 어휘 누락, V16의 신규 모집 근거 부재, V24의 규정·서식 모집 오인을 재현했다.
- 전체 서비스/API·브라우저를 통해 분류 화면을 검증한 것은 아니다. 이번에는 운영 코드 변경이 없으므로 전체 테스트를 다시 실행하지 않았다.
- 원문·연락처를 포함하는 스냅샷은 Git 제외 경로 `backend/build/business-type-audit/stored-43/`에만 두었다. 이 문서에는 비밀키·접속 정보·개인 연락처를 기재하지 않았다.

로컬 조사 산출물: `snapshot.json`(읽기 전용 DB 스냅샷), `decisions.json`(26건 수정 전후 재현), `rule-probes.json`(세 원인 재현), `input-audit.json`(현재 설정 가정의 입력 선택). 이들은 과거 실행의 실제 프롬프트·원시 응답 로그를 대신하지 않는다.
