# 신청자격 누락 단계 추적 — 2026-11-20

## 확인 범위

[원본 대조 검수](eligibility-accuracy-2026-11-20.md)의 10:06:37 스냅샷을 그대로 사용했다. 저장된 첨부 추출문, Java 원문 후보/송신 요청, 현재 Python의 순수 선별·메시지 생성 함수, 저장된 검증 후 응답, Java/프런트 표시 결과를 비교했다. 제품 코드·DB를 변경하거나 모델을 다시 호출하지 않았다.

모델 호출 당시의 전체 메시지와 검증 전 원응답은 이 스냅샷에 없다. 아래 모델 입력은 **현재 코드로 재구성한 입력**이다. 캐시의 모든 본문 source_id가 재구성한 선택 목록에 포함되는 것은 확인했다. 따라서 역사적 원응답의 토큰 소진이나 제공자 동작까지 확정하지 않는다. 46개 누락 전체를 하나의 원인별 비율로 배분한 결과도 아니다.

## 주요 원인

원문 텍스트에 존재하는 조건이 **모델 입력 선별에서 제외되는 경우**, **선별된 원문에 있지만 저장 응답에 없는 경우**, **요약의 불완전함을 검증이 감지하지 못하는 경우**를 각각 확인했다. 사업 분야가 깨지는 현상은 별도의 Java 표시 변환 문제다.

### 1. 원문 선별이 자격 조건을 제거한다

`ai/app/domains/participation/focused.py`는 원문 합계 8,000 UTF-8 바이트, 전체 입력 20,000바이트, 최대 24구역으로 제한한다. `selection.py`는 한 구역 자체가 8,000바이트를 초과해도 통째로 건너뛴다. 한글 8,000자가 아니다.

| 공고 | Java 송신 후보 구역 | Python 선택 구역 | 선택 원문 바이트 |
|---|---:|---:|---:|
| 창업패키지 수정 v4 | 21 | 5 | 7,303 |
| 창업패키지 원 공고 v5 | 22 | 5 | 7,718 |
| 스마트제조 v6 | 52 | 21 | 7,968 |
| 창업도시 v7 | 22 | 1 | 5,745 |

구역 수 감소 자체는 오류율이 아니다. 중복·무관한 내용도 후보에 포함된다. 문제는 실제 필수 요건이 포함된 아래 구역도 제외된다는 점이다.

- **창업도시 전담인력**: `s10`의 12,806바이트 구역에 정규직 최소 3인, 경력 5년 이상 최소 3인, 업무별 각 1인, 총괄책임자 직급/겸직 조건이 모두 있다. 선별 전 텍스트에는 남아 있지만 8,000바이트 초과로 선택되지 않는다. 앞부분 주거공간 지원과 뒷부분 지원사항·과업까지 같은 구역에 묶여 있다.
- **창업도시 대표도시·추진단 상세**: `s7`은 15,708바이트여서 제외된다. 연접한 최대 2개 시, 부산·세종 예외, 추진단장 지정, TIPS 운영사 필수 포함 등이 이 구역에 있다. 모델에는 요약표를 포함한 `s3`만 남는다.
- **제목 필터**: 스마트제조 `s11`의 1회차 성공 후 2회차 지원, `s13`의 유형 택일·데이터 준비, `s34`의 DX 단계별 대상 등은 `지원 내용 및 조건` 제목 아래 있다. `selection.prepare()`가 이 제목을 무관 구역으로 처리하여 제외한다. 창업패키지 `선정 규모` 아래 중복 신청·수행 제한 및 권역 선택 기준도 같은 유형의 문제다.
- **우선순위 5는 단순히 나중에 읽는 순서가 아니다**: `selection.select()`의 `priorities`는 0~4 후보가 하나라도 있으면 5를 순회하지 않는다. 스마트제조 `s17`(368바이트), `s20`(323바이트)의 상생기관·주관기관 조건, 창업도시 `s5`의 모집유형 택일은 이 이유로 제외된다. 작은 구역도 빠지므로 바이트 상한만 올려서는 해결되지 않는다.
- **유의사항의 실제 자격**: 창업도시 `s17`의 전남창조경제혁신센터 지정과 중앙정부 협의 조건도 `신청 시 유의사항` 필터에서 제외된다.

이는 확인한 사례에서 OCR이 글자를 못 읽은 문제가 아니다. 추출문/Java 송신 원문에 내용이 있고, Python 선별에서 빠진다. 다만 원문 구역이 크게 묶이고 잘못된 상위 제목을 물려받는 구조화 문제는 선별 실패를 악화시킨다.

### 2. 입력에 있는 조건도 모델 응답에서 축약된다

- 창업도시 `s3`의 `최소 15개 이상(기본 5개 외 10개 주요 과업항목별 1개 이상)`이 입력에 있지만 저장 응답에는 `최소 15개 이상`만 남고 details가 비어 있다.
- 창업패키지 수정 `s10`/`s16`은 전담조직장 선임 기준, 전문성, 겸직 자율 조건을 그대로 포함한다. 저장 응답은 주요 인원수와 확보 기한 중심으로 정리되어 일부 조건이 없다.
- 스마트제조 수준확인 보충 원문에는 참여기업뿐 아니라 확인기관, 교육·심의기관 역량이 들어 있고 선택도 된다. 저장 응답에는 참여기업 조건만 있다.
- 스마트제조 `s30`의 `국내 중소·중견기업`은 선택된 원문에 있으나 공급기업 역량진단 응답에서 빠졌다.
- 확정적인 제외를 `제외될 수 있습니다`로 완화한 표현도 저장된 응답에 이미 있다.

4개 응답의 진단은 각각 후보/수용 **13/13, 13/13, 11/11, 6/6**, unresolved 0이며 거절 사유가 없다. 이번 저장본의 주요 조건 누락을 `QUOTE_TOO_LONG` 검증에서 대량 삭제된 결과로 설명할 수 없다. 사용자가 앞서 제공한 08:55 로그의 거절 1건과 현재 스냅샷은 구분해야 한다.

### 3. 검증은 전체 조건의 보존을 보장하지 못한다

`focused.project()`는 인용의 원문 존재 여부, 길이, 일부 근거·문장 검사 등을 수행한다. `completeness.review_reason()`도 주로 법령 대안과 제재 효과의 제한된 오류를 확인한다. 원문 전체의 각 조건이 출력에 대응하는지 확인하는 일반 검사는 없다.

`completeness.qualification_rows()`의 표 누락 검사는 `[표]` 안의 **정확히 2열**이고 특정 제목을 가진 표만 인식한다. 이번 4개 공고의 재구성 입력에서 필수 확인 행으로 인식된 수는 **모두 0개**였다. 창업도시 3열 표와 창업패키지 4열 인력 표는 이 검사 대상이 아니다.

따라서 인용이 참인 문장 일부만 만들고 나머지 조건을 놓쳐도 `READY`/`VERIFIED`가 될 수 있다. `evidence_only_ids`에 미포함 출처를 넣지만, 그것이 구체적으로 어떤 자격을 놓쳤는지 검증하거나 재추출하지 않는다. Java의 `EVIDENCE_ONLY`는 조건 문장이 비어 있으며 프런트의 자격 목록에는 나오지 않는다. 독립 첨부 확인 화면을 되살리는 것으로 추출 누락이 해결되지는 않는다.

### 4. 사업 분야 오류는 Java 표시 변환에서 추가된다

창업도시 6개 저장 문장의 `scope`는 모두 `창업도시 조성 프로젝트`다. 출처의 상위 구역에는 `(제출서류) 1)사 사업`이라는 잘못된 제목이 들어 있다. `ParticipationProgramScope.resolve()`가 인용 위치에서 찾은 이 문맥을 반환하고, `ParticipationRewriteProjection`이 모델의 정상 사업명 대신 이를 표시용 scope로 사용한다. 프런트는 받은 값을 보여 준다.

이 현상은 자격 문장 생성과 별개로, 문서 추출 구역의 상위 제목과 조회 시 사업명 보정 양쪽을 점검해야 하는 문제다.

### 5. 일부는 현재 지시와 검수 범위의 불일치다

앞선 누락 46개에는 신청기관 대표자/총괄책임자 명의·계정 조건 3개(v4-C29, v5-C29, v7-T18)가 포함된다. 현재 프롬프트는 회원가입·계정/권한·전산등록을 필수라도 절차로 제외하라고 명시한다. 이 3개는 일반 자격 추출 실패와 분리해, 신청 안내 쪽에서 제공할지와 검수 범위를 맞춰야 한다. 나머지 자격·예외·인력 누락을 설명해 주는 사유는 아니다.

## 수정 우선순위와 한계

1. 원문을 실제 조건·표·각주 단위로 나누고, 상세 구역을 통째로 버리는 선별을 수정한다. 제목만으로 지원조건·유의사항을 제외하거나 우선순위 5를 전부 건너뛰는 동작도 함께 해결해야 한다.
2. 선택한 원문 조건별로 주체·범위·숫자·예외가 출력에 대응하는지 검증한다. 임의 요약과 두 열 표 전용 검사에 의존하는 현재 구조를 보완한다.
3. 사업명 보정은 잘못된 문서 제목이 정상 모델 사업명을 덮어쓰지 않게 수정한다.
4. 접수 명의/계정 조건은 신청자격과 신청 안내 중 제공 위치를 일치시킨다.

프롬프트만 구체화하거나 타임아웃만 늘리는 것으로 1번 문제는 해결되지 않는다. 앞선 45초 취소는 결과가 통째로 없는 원인이었고, 이번에는 READY 결과 내부의 정보 누락을 조사했다. 재생성 후 실제 개선률은 아직 측정하지 않았다.
