# 제출 조건·신청 자격 프롬프트/코드 계약 점검 (2026-11-17)

## 실제 저장 결과에서 확인한 사실

DB를 읽기 전용으로 조회했다. 제보 공고 version 12의 신청 자격 캐시는 `READY`, `statements=[]`, 근거 전용 ID 15개였다. 현재 입력과 캐시 키는 일치했다. Python 입력 선택을 재현하면 신청 자격 표와 제외 대상이 포함된 4개 출처가 남는다. 따라서 이번 현상을 원문 미수집이나 프런트 문체 필터 때문이라고 단정할 수 없다. 직전 실행의 모델 원응답은 저장돼 있지 않아 빈 생성인지 전체 인용 검증 실패인지까지는 확정하지 못했다.

제출 조건 캐시는 `PARTIAL`, 공통 안내 4개이며 문제 서류에 연결된 DOCUMENT 안내는 없다. 화면에 나온 문장은 AI 결과가 아니라 `SubmissionDocumentDisplay`의 원문 서류명 조건을 `SubmissionNotesProjection`이 보존한 결과다. 기존 회귀 테스트도 이 반복을 유지하도록 요구했다.

## 확인한 충돌과 변경

1. 본문 작성 지시와 달리 `ExtractedCondition.text`가 nullable/선택 필드였다. 필수 비어 있지 않은 string으로 맞췄다. 레거시/모의 객체의 잘못된 text는 계속 근거 검증에서 거절한다.
2. quote에는 줄 번호만 허용하면서 별도 지시는 원문을 quote에 보존하라고 했다. `quote=L2 또는 L2-L4`, 코드가 원문을 복원한다고 명시했다. source_id는 sources의 실제 ID이며 recruitments는 출처가 아님을 명시했다.
3. 세부 설명에 대체 자격·법령을 넣으라는 지시와 정의·증빙·예외만 허용한다는 지시를 통일했다. 핵심 요건은 text에, 추가 자격 범위·정의·법령·증빙·예외는 details[].text에 쓴다.
4. 자격 근거가 있는데 결과가 없거나 모든 후보가 거절돼도 READY가 됐다. 관련 근거의 빈 추출은 UNAVAILABLE로 처리하고, 후보/승인/거절 사유별 건수만 diagnostics로 반환·저장한다. 원문이나 모델 내부 추론은 진단 필드에 저장하지 않는다. 기존 READY+빈 항목+미해결 근거 캐시도 표시 시 UNAVAILABLE로 구별한다.
5. 서류명과 똑같은 조건을 무조건 보존하던 대체 표시를 보완했다. 원문에 그대로 있는 서류명 중 명시적인 `서류명(대상 해당 시)` 구문만 문장으로 펼친다. 동반 서류의 의무·예외는 추가하지 않는다. 선택 관계·중첩 괄호·불명확한 단서는 추정하지 않으며 기존 근거를 유지한다. 특정 공고명/법인 서류명을 분기 조건으로 사용하지 않는다. 유효한 AI 설명이 전체 제목을 설명하면 기존처럼 AI 설명을 사용한다.
6. 제출 조건 프롬프트는 문서 목록의 괄호 단서를 먼저 설명한 뒤 나머지 안내를 확인하도록 정리했다. A서류의 조건을 같은 행의 B서류까지 확대하지 않는다.
7. 생성 계약을 변경했으므로 신청 자격 정책을 `participation-condition-contract-v6`, 제출 조건 정책을 `submission-notes-contract-v2`로 변경했다. 원문이나 다른 분석 데이터는 무효화하지 않는다. 기존 잘못된 캐시를 새 프롬프트 결과처럼 계속 재사용하지 않는다. 서비스가 새 코드를 로드한 뒤 상세 조회하면 변경된 정책당 1회 생성하며 같은 정책의 실패를 자동 재시도하지 않는다.

## 확인한 표시 결과

현재 저장 데이터를 새 Java 코드로 재생하면 문제 제출 조건은 다음과 같다.

> 법인등기부 등본은 법인에 해당하는 경우 제출해야 합니다.

사업자등록증까지 법인 조건을 확대하지 않는다. 서류 목록의 행, 원문, 부수, 시기는 보존한다. 빈 신청 자격 결과는 미완료로 구별하며 새 자격 문장을 임의로 만들어 채우지 않는다. 이 확인은 새 모델 생성 성공을 의미하지 않는다.

## 비용과 검증

모델 gpt-5-mini/low, 각 기능 1회, 자동 재시도 0회, 신청 자격 출력 4096토큰/제출 조건 6000토큰 등 상한은 유지했다. 동일한 제보 입력의 로컬 o200k_base 추정 입력은 신청 자격 4118→4122토큰(+0.10%), 제출 조건 13061→13145토큰(+0.64%)이다. 실제 청구 비용/출력 토큰 비교가 아니다.

- AI 관련 테스트 405개 및 Ruff 통과.
- 현재 DB 읽기 전용 스냅샷과 새 코드 재생 결과 비교. DB 쓰기 없음.
- 대체 API를 사용한 브라우저 1440/390/320px 확인: 제출 조건 문장, 자격 미완료 표시, 가로 넘침 없음.
- 백엔드 전체 1793개 통과(실패·오류·건너뜀 0). 첫 전체 실행에서 초안 저장 테스트 1개가 실패했으나 해당 영역은 수정하지 않았고 전체 재실행에서 통과했다.
- 이번 작업의 추가 승인 2회를 사용했다. 신청 자격·제출 조건 각각 1회이며 자동 재시도 0회, DB 쓰기 0회다. 이후 수량 검사 수정은 이 실제 응답을 로컬 재생해 확인했으며 추가 유료 호출은 없다.

재현 자료는 로컬 `backend/build/prompt-contract-audit-20261117/`에 있다. current.json은 수정 전 저장 데이터, after.json은 읽기 전용 재생, cost.json은 로컬 비용 추정이다.

## 추가 승인된 실제 2회 검증에서 확정한 원인

신청 자격은 후보 8개가 모두 채택됐고 4개 신청 요건(3개 주체와 신청 형태) 및 4개 제외 조건이 실제 화면까지 표시됐다. 검토 전/후 응답을 함께 보존해 거절 여부를 구분했다. 본문/세부 설명은 형식 검사를 통과했지만 일부 의미상 반복은 남아 있다. 원문 일치·형식 검증이 모든 문장의 의미 정확성이나 요약 품질을 보장하는 것은 아니다.

제출 조건 모델은 서류별 설명 5개를 실제 생성했다. 그러나 수량 검사에서 `5\t서류명\t각 1부\t기관별 1부`의 순번 5와 반복 수량 1을 그대로 세어, 정상 설명의 `1부`와 다르다는 이유로 거절했다. 이 원인은 추측이 아니라 검증 전 응답을 재생해 확인했다.

Python과 Java의 숫자 비교를 같은 규칙으로 맞췄다. 인용이 카탈로그의 정확한 원본 행이고 `숫자 순번 / 동일 서류명 / 부수 / 비고`의 4개 탭 열일 때만 순번을 비교에서 제외한다. 부수와 비고의 `대상별 동일 부수`가 정확히 반복될 때만 한 번 비교한다. 수량·단위 변경, 누락, 서로 다른 부수, 별도 원본 부수, 서류명 안 숫자는 계속 검증한다. 저장 인용 원문은 수정하지 않는다. 공통 JSON 사례를 Python/Java 테스트가 공유한다. 프롬프트도 순번과 같은 수량 반복을 설명에 옮기지 않도록 맞췄다.

같은 실제 응답의 로컬 재생 결과 서류별 설명 5개가 통과했다. 3개 공통 안내는 불연속 인용 또는 의미 누락 때문에 계속 거절했고 PARTIAL을 유지한다. 문제 서류의 화면 설명은 “법인에 해당하는 경우에는 법인등기부 등본을, 그리고 모든 해당 기관은 사업자등록증을 각 1부씩 기관별로 제출해야 합니다.”이다. 생성된 전체 안내가 정확하다고 확정하지 않는다.

실제 호출 토큰: 신청 자격 입력 3933/출력 1807, 제출 조건 입력 12321/출력 2808, 합계 20869. 최종 수량 지시 보완은 추가 호출 없이 기존 실제 응답의 검증 경로와 회귀 테스트로 검증했다. 실제 응답 재생 화면도 1440/390/320px에서 확인했다. 운영 캐시를 수동 변경하지 않았고, 실행 중인 AI 서비스는 이전 코드를 로드한 상태이므로 수정 반영에는 서비스 재기동이 필요하다. 현재 로컬 DB 설정의 ddl-auto=create와 14:26 테이블 재생성을 확인했으므로 DB를 지우는 서버 재시작은 수행하지 않았다. 8080 종료는 저장소 작업 마무리 지침에 따른다.
