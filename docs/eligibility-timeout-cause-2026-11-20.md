# 신청자격 누락 원인과 수정 (2026-11-20)

기존 저장 결과의 복원이 아니라 원인을 추적했다. 제품 DB에는 쓰지 않았으며 실제 모델 API를 추가 호출하지 않았다.

## 확인한 원인

1. **재시작 시 저장 데이터 삭제**: 로컬 `backend/src/main/resources/application.properties`와 실행용 리소스의 `spring.jpa.hibernate.ddl-auto`가 `create`였다. 읽기 전용 Oracle 조회에서 `DOCUMENTS`, `DOCUMENT_ATTACHMENTS`, `DOCUMENT_VERSIONS` 모두 생성 시각이 `2026-11-20 08:38:41`, 마지막 DDL 시각이 `08:38:42`로 확인됐다. 이전 07:37 스냅샷의 결과와 이후 수집 결과를 같은 저장 결과로 취급할 수 없다. 버전 ID가 다시 12라는 이유로 이전 캐시가 유지됐다고 판단하면 안 된다.
2. **새 신청자격 응답을 받기 전 45초 취소**: 사용자가 제공한 로그의 호출 `6414bff3c4ca`는 `08:52:53.828`에 모델 대기를 시작했고 `08:53:38.836`에 `TimeoutError`, `timeout_kind=local_deadline`, `elapsed_seconds=45.015`, `response_received=false`, `stage=model_wait`로 종료됐다. 응답의 인용 검증이나 의미 검증에서 전체가 거절된 상황이 아니다. `SSLWantReadError`는 취소 당시 읽기 대기 문맥이며 이 로그만으로 TLS 인증서 장애를 의미하지 않는다.
3. **실패 결과 재사용**: `ParticipationRewriteService`는 같은 입력의 `UNAVAILABLE`를 저장하고 이후 조회·재시작에서도 재사용한다. 따라서 화면 새로고침만으로 생성이 재개되지 않는다. 이는 자동 중복 과금을 막는 기존 정책이다.
4. **원치 않은 별도 화면**: ‘첨부 자격 확인’은 직전 작업에서 추가한 독립 UI였다. 실제 신청자격 생성 성공 여부와 관계없이 확인서 원문을 보여주는 경로였으므로, 실패 상태에서 이 부분만 보일 수 있었다.

현재 스냅샷 재생에서 12번 공고는 24개 전송 후보 중 11개 원문을 선택했다. 신청 주체 표의 협회·단체/연구기관/기업지원기관 3행, 제외 조건, 확인서와 공고 예외가 포함된다. 원문은 7,884/8,000 UTF-8바이트, 전체 직렬화 입력은 16,885/20,000바이트로 한도 이내다. 원문 3,403자·메시지 7,131자는 제공된 실패 로그와 정확히 일치한다. 입력 한도 초과나 자격표 전체 누락이 해당 실패의 원인은 아니다.

같은 로그의 다른 작업은 66~78초 뒤 정상 응답을 받았지만, 이것만으로 신청자격도 그 시간에 성공했을 것이라고 단정하지 않는다. 공급자 내부에서 응답이 오래 걸린 이유와 45초 이후의 실제 완료 시간은 확인할 수 없다.

## 수정

- 로컬 재시작 설정을 `ddl-auto=none`으로 변경하여 기존 테이블을 보존한다. 이 설정 파일은 Git 추적 대상이 아니며 비밀 설정을 문서나 커밋에 포함하지 않는다.
- 신청자격 호출 제한 45→120초, 대기열을 포함한 문서 전체 제한 60→150초, Java의 저장 PENDING 만료 120→180초로 맞춘다. 제한 없는 대기로 변경하지 않는다.
- 기존 응답 `diagnostics`에 실패 코드와 건수를 남긴다. `MODEL_TIMEOUT`, `DOCUMENT_TIMEOUT`, `MODEL_ERROR`, `RESPONSE_INVALID`, `INPUT_BUDGET_EXCEEDED`, `MODEL_NOT_CONFIGURED`를 구분한다. 원문·응답 전문·예외 메시지는 저장하지 않는다.
- 독립 ‘첨부 자격 확인’ 화면과 전용 데이터 표시 도우미를 제거한다. 신청 구분·적용 사업·정상 조건·세부 설명·조건별 원문 보기는 유지한다.
- 모델·추론 강도·출력 4,096토큰·입력 상한·호출 1회·재시도 0회·캐시 키는 유지한다. 기존 실패 캐시를 삭제하거나 과거 정상 결과로 덮어쓰지 않는다.

직전 완전성 검사가 과거 8조건 중 법적 대안 누락과 제재 범위 확대 2항목을 원문 확인 안내로 바꾸는 동작은 별도로 존재한다. 이것은 이번 새 결과 전체가 0건인 원인과 구분한다. 확인된 부정확한 문장을 다시 정상 조건으로 노출하지 않는다.

## 검증

- AI 신청자격 410개와 변경 Python 파일 Ruff 통과. 동일한 지연 응답이 기존 45초/60초에서는 시간 초과, 새 120초/150초에서는 성공하는 경우를 축약 시간과 대체 모델로 검증했다. 대기열 전체 시간 초과, SDK 읽기 시간 초과, 모델 오류, 잘못된 응답, 입력 한도, 키 누락도 구분한다.
- 프런트 110개·build·lint 통과. 1440/390/320px에서 READY와 UNAVAILABLE를 대체 GET API로 재생하여 독립 확인 화면 제거, 정상 결과의 8행·신청 구분·설명·원문 보기 유지 및 가로 넘침 없음을 확인했다.
- 백엔드 전체 1,824개 통과(실패·오류·건너뜀 0). 재시작 후 저장 PENDING가 130초에도 진행 중으로 남고 180초 이후 종료되는 경계와 자동 중복 호출 방지 검사를 포함한다. `processResources` 후 실행용 설정도 `none`임을 확인했다.

현재 저장된 UNAVAILABLE는 그대로이며 새 시간 제한으로 실제 모델 생성에 성공했다고 주장하지 않는다. 기존 데이터 소실분도 복원하지 않았다. 로컬 재현 산출물은 Git 제외 폴더 `backend/build/eligibility-display-restore-20261120/`에 있다. 폴더 이름은 초기 조사 중 정해진 이름이며 복구 실행을 의미하지 않는다.

작업 종료 시 8080 리스너 PID 2420과 작업용 미리보기 PID 46476을 종료했으며, 8080 포트가 비어 있음을 확인했다.
