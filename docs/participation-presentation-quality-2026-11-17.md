# 신청 자격 세부 설명의 문장 품질 보완

## 확인한 원인

저장된 결과가 본문을 반복하거나 명사형 원문·주석을 세부 설명에 복사했다. 원문 인용과 길이 검사만으로는 문체 지시 위반이 차단되지 않았다. 접수 방법의 기관등록·담당자 권한 안내도 신청 주체에 섞여 있었다. 화면의 줄바꿈만 바꾸어 해결할 문제가 아니다.

## 구현

- 시스템 지시는 핵심 요건을 본문에 유지하고, 본문에 없는 정의·증빙·예외를 설명별 완결 문장으로 작성하도록 정리했다. 인용 보존과 표시문 작성의 역할을 분리했다. [OpenAI 공식 지침](https://developers.openai.com/api/docs/guides/reasoning-best-practices)의 명확하고 구체적인 지시 원칙을 참고했다.
- Python은 인용 검증 뒤 본문·설명의 문장 형식을 검사해 `review_required`를 반환/저장한다. 생성용 `Extraction` 스키마에는 이 필드를 추가하지 않았다. 명사형 조각에 어미를 붙이거나 검증 실패 항목 때문에 추가 호출하지 않는다.
- Java는 새 응답과 기존 캐시 모두 같은 형식 기준으로 검사한다. 구형 캐시의 누락/null 검토 필드는 호환해 읽는다. 본문 실패는 `REVIEW_REQUIRED`, 설명 실패는 정상 설명 목록에서 제외하고 원문 확인 안내를 제공한다. 모든 유효 인용과 출처는 원래 항목에 유지한다.
- 정확히 같은 본문·설명의 공백 차이만 중복 처리한다. 같은 인용을 쓴다는 이유로 정의·법령·예외를 없애지 않는다. 의미가 같은 재진술의 완전한 판별은 보장하지 않는다.
- 접수 방법 구역의 계정·권한·전산등록 안내를 `APPLICATION_GUIDANCE`로 분리한다. 법적 등록·허가·자격·업력·체납 조건이 혼재하면 자격에 유지한다. 특정 공고명·IRIS 등의 시스템명 분기는 없다.
- 화면은 정상 설명을 항목별로 표시한다. 본문 형식 실패 시 원문 확인 문장을 보여주며, 설명 실패 시 정상 본문·형제 설명과 원문 확인 안내를 함께 표시한다. 원문 근거는 직접 펼쳐 확인할 수 있다. 접수 준비 안내는 신청 주체 조건 수에 포함하지 않는다.

## 적용과 비용

백엔드·프런트 반영 후 기존 캐시도 표시 단계에서 검사한다. 이전의 잘못된 설명을 새로운 문장으로 자동 재작성하는 기능은 아니다. AI 재시작 후 신규 추출부터 새 프롬프트를 사용한다. DB 캐시를 수동 보정하거나 일괄 재생성하지 않았다.

모델 gpt-5-mini·low, 최대 1회 호출, 재시도 0회, 출력 4096토큰과 기존 입력 상한·캐시 키를 유지했다. 추가 유료 호출은 0회다. 실제 저장 요청을 로컬 o200k_base로 계산했을 때 시스템 지시는 699→780토큰, 스키마를 포함한 전체 입력은 4036→4118토큰(+82, 약 2.0%), UTF-8 직렬화 크기는 14541→14863바이트다. 출력·추론 길이·실제 청구액은 측정하지 않았다.

## 검증

- AI 참여조건·제출 관련 392개 통과, 변경 Python 파일 Ruff 통과.
- 프런트 전체 109개·빌드·린트 통과.
- 실제 저장 결과를 파일에서 재생해 신청 주체/참여 형태 4개, 접수 준비 안내 1개, 제외 4개의 분리를 확인했다. 저장되어 있던 세부 설명 9개는 명사형 원문이어서 확인 안내로 표시하고 근거를 보존했다.
- 대체 API 브라우저 검사로 1440/390/320px에서 분류·원문 버튼·확인 안내·가로 넘침을 확인했다. 정상 설명을 담은 별도 대체 응답은 항목 2개가 각각 표시되는지 검증했다. 이 결과를 실제 모델의 새 문장 생성 성공으로 간주하지 않는다.
- 백엔드 전체 최종 실행 1787개 통과(실패·오류·건너뜀 0). 과거 명사형 출력을 정상으로 기대하던 테스트는 검토 상태 계약에 맞춰 변경했으며 캐시·동시성 테스트의 정상 표본은 완결 문장으로 갱신했다.

아티팩트는 Git 제외 `backend/build/participation-details-audit-20261117/`의 `projected-quality.json`, `quality-cost.json`, `quality-{width}.png`에 있다. 실제 모델의 새 생성 품질·운영 서버 재시작 후 화면은 검증하지 않았다. 형식 검사는 의미 정확성, 모든 중복 제거, 모든 접수 절차의 완전한 분리를 보증하지 않는다.

로컬 `application.properties`의 `ddl-auto=create`는 이번 범위에서 변경하지 않았다. 백엔드를 재시작하면 DB가 초기화되는 설정이므로 기존 결과 보존이 필요한 경우 변경 반영 전에 이 설정을 확인해야 한다. 이번 검증은 저장 표본 파일·대체 API·테스트 DB를 사용했다.
