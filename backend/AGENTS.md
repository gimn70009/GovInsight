# GovInsight 백엔드 개발 지침

## 적용 범위

- 이 문서는 `backend/` 아래의 모든 파일에 적용한다.
- 루트 `AGENTS.md`의 공통 규칙을 함께 따른다.
- 두 규칙이 충돌하면 이 문서의 백엔드 전용 규칙을 우선한다.

## 기술 기준

- Java 21과 현재 프로젝트에 설정된 Spring Boot 버전을 사용한다.
- 빌드와 테스트는 Gradle Wrapper로 실행한다.
- 데이터 접근은 Spring Data JPA와 PostgreSQL을 기준으로 한다.
- 새로운 라이브러리는 기존 기능으로 해결하기 어려울 때만 추가한다.
- 라이브러리를 추가할 때는 사용 목적을 `build.gradle`에서 알 수 있게 정리한다.

## 패키지 구조

- 패키지는 계층만으로 묶지 않고 도메인 기능을 기준으로 구성한다.
- 도메인 코드는 `domain/<도메인명>` 아래에 둔다.
- 여러 도메인에서 함께 사용하는 코드는 `global` 아래에 둔다.

```text
com.publicmonitor.backend
├─ domain
│  └─ <domain>
│     ├─ entity
│     ├─ repository
│     ├─ service
│     ├─ exception
│     └─ web
│        ├─ controller
│        └─ dto
└─ global
   ├─ config
   ├─ entity
   ├─ exception
   ├─ response
   └─ security
```

- 특정 도메인에서만 사용하는 클래스는 편의를 이유로 `global`에 두지 않는다.
- 패키지명은 소문자로 작성하고 하나의 명명 방식으로 통일한다.

## 계층별 책임

### Controller

- HTTP 요청 수신, 입력 검증, 서비스 호출, 응답 반환만 담당한다.
- 비즈니스 규칙과 데이터 접근 로직을 작성하지 않는다.
- 요청 값은 Request DTO로 받고 응답 값은 Response DTO로 반환한다.
- Entity를 요청 또는 응답 객체로 직접 사용하지 않는다.
- 요청 DTO에는 Jakarta Validation을 적용하고 Controller에서 `@Valid`로 검증한다.

### Service

- 비즈니스 규칙과 유스케이스 흐름을 담당한다.
- 트랜잭션 경계는 Service 계층에 둔다.
- 조회 작업에는 가능한 경우 `@Transactional(readOnly = true)`를 사용한다.
- 단순히 형식을 맞추기 위한 Service 인터페이스는 만들지 않는다.
- 구현체 교체 가능성이나 명확한 경계가 있을 때만 인터페이스와 구현체를 분리한다.

### Repository

- 데이터 저장과 조회만 담당한다.
- 화면이나 API 응답 형식을 Repository에 노출하지 않는다.
- 복잡한 조회는 메서드 이름을 억지로 늘리지 말고 의도가 드러나는 별도 조회 방식으로 분리한다.

### Entity

- 상태 변경은 의미가 드러나는 메서드를 통해 수행한다.
- 외부에서 필드를 임의로 변경할 수 있는 공개 setter를 만들지 않는다.
- 연관관계는 실제 조회와 변경 흐름을 기준으로 필요한 것만 설정한다.
- `equals`, `hashCode`, `toString`에서 지연 로딩 연관관계를 무분별하게 참조하지 않는다.

## DTO와 응답

- DTO 이름은 역할이 명확하게 드러나도록 `<기능>Request`, `<기능>Response` 형식을 사용한다.
- `Req`, `Res`, `Dto`를 혼용하지 않는다.
- 단순 데이터 전달 DTO는 Java `record` 사용을 우선 검토한다.
- 성공 응답과 오류 응답은 프로젝트 공통 형식을 사용한다.
- 페이징 응답은 데이터 목록과 페이지 정보를 일관된 구조로 제공한다.
- 내부 예외 메시지, 스택 트레이스, DB 정보는 API 응답으로 노출하지 않는다.

## 예외 처리

- 예상 가능한 비즈니스 오류는 도메인별 예외와 오류 코드로 표현한다.
- Controller에서 개별적으로 `try-catch`하지 않고 전역 예외 처리기를 사용한다.
- 존재하지 않는 리소스, 잘못된 상태 변경, 중복 등록을 서로 구분한다.
- 모든 예외를 일반 `RuntimeException` 하나로 처리하지 않는다.
- 서버 오류는 로그에 원인을 남기되 클라이언트에는 안전한 메시지만 반환한다.

## 외부 연동

- Spring Boot와 Python 모듈의 역할 및 통신 흐름은 `docs/architecture.md`를 따른다.
- Python 수집·분석 모듈과 Telegram 같은 외부 시스템 호출은 전용 클라이언트 또는 어댑터로 분리한다.
- Controller나 Entity에서 외부 API를 직접 호출하지 않는다.
- 외부 요청에는 연결 및 응답 타임아웃을 설정한다.
- 재시도는 멱등성이 보장되는 작업에만 제한적으로 적용한다.
- 외부 연동 실패가 발생하면 대상, 실행 ID, 원인을 추적할 수 있는 로그를 남긴다.
- API 키, 토큰, 비밀번호는 코드와 Git 추적 설정 파일에 작성하지 않는다.

## 코드 스타일

- 의존성 주입은 생성자 주입을 사용한다.
- Lombok을 사용할 때는 코드의 의도를 숨기지 않는 범위에서 사용한다.
- 메서드는 한 가지 책임을 가지도록 작성한다.
- 이름으로 의도를 충분히 표현하고, 코드 내용을 반복 설명하는 주석은 작성하지 않는다.
- 중요한 정책이나 예외적인 판단에는 이유를 설명하는 주석을 작성한다.
- 미사용 코드, 주석 처리된 코드, 디버깅 출력문을 커밋하지 않는다.

## 테스트와 검증

- 비즈니스 규칙에는 단위 테스트를 작성한다.
- Repository의 복잡한 조회에는 데이터 계층 테스트를 작성한다.
- Controller의 요청 검증과 응답 상태는 웹 계층 테스트로 확인한다.
- 외부 API, AI 모듈, Telegram 호출은 기본 테스트에서 실제로 호출하지 않고 대체 객체를 사용한다.
- 테스트가 로컬 PostgreSQL 비밀번호에 의존하지 않도록 테스트 전용 설정을 사용한다.
- 변경 후 `backend/`에서 다음 명령을 실행한다.

```powershell
.\gradlew.bat test
```

- 테스트를 실행하지 못했거나 실패한 경우 완료된 것처럼 보고하지 않고 원인을 명시한다.

## 문서 동기화

- 구현 전에 `docs/architecture.md`, `docs/monitoring-process.md`와 작업에 관련된 설계 문서를 확인한다.
- 구현과 프로젝트 문서가 충돌하면 임의로 판단하지 않고 사용자에게 알린다.
- API 계약이 변경되면 API 문서도 함께 수정한다.
- 테이블이나 연관관계가 변경되면 데이터베이스 설계 문서도 함께 수정한다.
- 백엔드와 AI 모듈 사이의 요청·응답 형식이 변경되면 양쪽 관련 문서를 함께 확인한다.
- 모니터링 처리 규칙이 변경되면 `docs/monitoring-process.md`도 함께 수정한다.
- 아직 결정되지 않은 기술이나 구조를 확정된 규칙처럼 추가하지 않는다.
